## The semantic boundary

The relevant equivalence relation is not:

$$
\operatorname{digest}(A)=\operatorname{digest}(A')
$$

It is closer to:

$$
\operatorname{Meaning}(A, E, P, t)
$$

Where:

- $A$ is the artifact population.
- $E$ is the semantic environment: dialects, evaluator implementation, dependency closure, capability set, defaults, and configuration.
- $P$ is the proposition being evaluated.
- $t$ is the relevant temporal coordinate: evaluation time, target-fact time, and external-data snapshot time.

Therefore:

```text
SAME_ARTIFACT_BYTES
  !=> SAME_SEMANTIC_EVALUATION_CONTEXT

SAME_SEMANTIC_EVALUATION_CONTEXT
  !=> SAME_PROPOSITION

SAME_PROPOSITION_RESULT
  !=> SAME_GOVERNANCE_DISPOSITION
```

The second non-implication matters because a technical result can be reused in a different authorization, authority, or continuing-standing question. Fork should treat that as a proposition change, not silently promote an old result into a current disposition.

## Source validation

Your OPA reading is well-founded. The bundle manifest can carry `revision`, `rego_version`, `file_rego_versions`, roots, Wasm entrypoints/modules, and arbitrary metadata. When no manifest Rego version is present, OPA uses v1 syntax unless run with `--v0-compatible`; manifest-level and per-file version declarations override that runtime flag; overlapping per-file glob patterns have undefined behavior.  OPA’s compatibility guidance also prefers setting Rego version at module or manifest granularity and says mixing v0 and v1 Go packages is unsupported.[^1_2][^1_1]

That establishes a useful Fork rule:

```text
OPA_POLICY_SOURCE_DIGEST
  !=> OPA_EVALUATION_IDENTITY
```

At minimum, OPA replay identity needs the bundle digest, manifest bytes or canonical manifest representation, OPA binary/image digest, runtime flags, Rego language selection, compiler target, entrypoint/query, input document, data snapshot, and builtin/capability profile. A Wasm result is especially not self-explanatory without its runtime/ABI and entrypoint binding.

Your JSON Schema analysis is also exact in its essential point. Draft 2020-12 distinguishes assertions, annotations, applicators, and identifiers; defines a dialect as vocabularies and their required-support status; says unknown keywords should normally be treated as annotations; and says schemas containing only unknown properties are empty schemas.  An implementation that does not recognize a *required* vocabulary must not process a schema using that dialect; when `$schema` is absent, dialect selection is implementation-defined.[^1_3]

The in-toto case complements rather than weakens the argument. Runtime Trace says consumers must ignore unrecognized fields, while major predicate-type revisions denote breaking changes and minor revisions are backward-compatible and monotonic. But `monitor.type` determines how `tracePolicy`, process, and network records are parsed, and the specification directly cautions that synchronous and asynchronous monitoring provide different assurance about file digests at use time.[^1_4]
