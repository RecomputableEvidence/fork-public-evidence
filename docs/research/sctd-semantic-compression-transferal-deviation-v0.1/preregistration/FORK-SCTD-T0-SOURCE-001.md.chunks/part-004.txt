## Final separations

The model should retain all three distinct boundaries:

```text
DECLARED_SEMANTIC_ENVIRONMENT
  !=> RESOLVED_SEMANTIC_ENVIRONMENT

ARTIFACT_AND_ENVIRONMENT_IDENTITY
  !=> PROPOSITION_IDENTITY

PARSING_SUCCESS
  !=> REQUIRED_SEMANTIC_FEATURE_CONSUMPTION
```

These close different failure classes:

- A declared evaluator image, vocabulary list, or data source may not identify the dependencies actually resolved at execution time.
- Identical artifacts and evaluator conditions can evaluate different propositions—for example, a historical decision proposition versus a present continuing-authority proposition.
- A processor can parse, structurally validate, and return success without enforcing the governance feature on which the downstream conclusion depends.


## Corrected consumption standing

Your revision from `FEATURE_IGNORED` to `FEATURE_IGNORED_OBSERVED` is essential. “Ignored” is an empirical claim about evaluator behavior, not a conclusion that can be inferred from an acceptance result.

```text
SEMANTIC_FEATURE_CONSUMPTION =
    ALL_REQUIRED_FEATURES_ENFORCED
  | REQUIRED_FEATURE_UNSUPPORTED
  | FEATURE_IGNORED_OBSERVED
  | FEATURE_CONSUMPTION_NOT_ESTABLISHED
  | INDETERMINATE
```

The key constraint is:

```text
VALIDATION_PASS
+ UNKNOWN_KEYWORD_PRESENT
  !=> FEATURE_IGNORED_OBSERVED
```

A generic implementation could have ignored the keyword, implemented a nonstandard extension with another meaning, performed undocumented handling, or simply not emitted evidence adequate to determine consumption. Therefore, absent a preserved trace, diagnostic output, capability declaration, or controlled differential test, Fork should report:

```text
SEMANTIC_FEATURE_CONSUMPTION =
  FEATURE_CONSUMPTION_NOT_ESTABLISHED
```

This preserves the distinction between an observed non-enforcement event and a lack of evidence about enforcement.

## Processing precedes validation

Separating meta-schema and dialect resolution from vocabulary refusal avoids another category error. A processor that cannot resolve the dialect has not necessarily examined the dialect’s vocabulary declaration; it therefore cannot truthfully be described as having refused an unsupported required vocabulary.

```text
PROCESSING_STATUS =
    PROCESSED
  | REFUSED_UNSUPPORTED_REQUIRED_VOCABULARY
  | DIALECT_UNRESOLVED
  | META_SCHEMA_UNAVAILABLE
  | SCHEMA_INVALID
  | PROCESSING_FAILED
  | INDETERMINATE
```

The ordering constraint should be explicit:

```text
PROCESSING_STATUS != PROCESSED
  => VALIDATION_RESULT = NOT_PRODUCED
```

And more narrowly:

```text
REFUSED_UNSUPPORTED_REQUIRED_VOCABULARY
  requires
    DIALECT_RESOLVED
    and REQUIRED_VOCABULARY_DECLARATION_OBSERVED
    and REQUIRED_VOCABULARY_SUPPORT_DETERMINED_ABSENT
```

This aligns with JSON Schema’s vocabulary mechanism: implementations must refuse to process a dialect when it declares a vocabulary as required and the implementation does not recognize that vocabulary. It does not justify calling all failures to resolve or retrieve a meta-schema “unsupported vocabulary” failures.[^2_1]
